# Writfold implementation

Writfold is the Rust successor to an earlier private prototype. This public repository contains the Rust product (the `writfold kb` verbs and `writfold watch`), its Aeneas proofs, its TLA+ models (`spec/KbWrite`, `spec/RunGraph`) and current planning. The prototype, the earlier handovers, and the components the binary no longer runs (the edit trial flow, `serve`, `writfold tuft`, `writfold.agent/1`, Dolt, Omnigraph) with their Lean models, qualification records, benchmark pilots and older TLA+ models are retained in the private archive `writfold-dev/writfold-archive`: with their history under `public-split-2026-11-16/`, and as the last buildable tree on its branch `public-main-pre-split` (tag `pre-split-2026-11-16` here). Tuft, Weft's assessed gate, Splicery's `kb edit` and the Verus formalization were removed on 21 November 2026 ([#54](https://github.com/writfold-dev/writfold/issues/54)); the last tree with them is the archive's branch `public-pre-cleanup-2026-11-21` (tag `pre-cleanup-2026-11-21` here).

## Mission and authority

- **The current authority is [`docs/writfold/mission.md`](docs/writfold/mission.md)** (owner decision, 11 November 2026): Git-native project continuity for agents. A cold session on any machine answers why / status / tracker / impact questions, each answer pinned to a source and marked when that source has moved. Git text is the source of truth; a local SQLite file is a derived index that can always be rebuilt. The v1 design is [`docs/writfold/kb-v1-design.md`](docs/writfold/kb-v1-design.md).
- **Acceptance test:** the owner replaces the private prototype with the `writfold` binary for real work. Benchmark pilots are paused; do not start new ones unless the owner asks.
- **Removed on 21 November 2026 (owner decision, [#54](https://github.com/writfold-dev/writfold/issues/54)):** Tuft, Weft (the assessed gate), Splicery (`kb edit apply`) and Verus, frozen since 15 November. Weft and Splicery live on in their own repositories. Do not reintroduce them; the `writfold kb` verb groups are the interface for each stage of the flow.
- **History, not obligations:** the archived gate programme, proof inventories and scenarios record what was done; they are not live work items. Never relabel an earlier receipt or convert a skipped, blocked or unrun obligation into a pass.
- Adopt private `private:playbook@e7d991e990e3dff9c5d70e4327c0e90298e2f67e` only at that pin (`scripts/gate` checks it). Do not publish private reference material or edit the playbook. The prototype's knowledge-base layout may be read for compatibility; describe formats in Writfold's own words and never copy its code or prose.

## Engineering and builds

- Linux/WSL x86_64. Target a static musl Rust executable; rustls-only dependencies; Git remains an explicit native dependency. No server or companion process on the product path.
- **Lean proofs first (owner, 16 November 2026).** Every decision the product makes (what counts as met, stale, ready, skipped, complete, refused or allowed) lives in a pure, IO-free kernel in `crates/writfold-core`, is extracted with Charon/Aeneas and has its properties proved in Lean (`proofs/`, `docs/writfold/aeneas.md`). New or changed decision logic is proved, and the proofs gate passes (drift check, `lake build`, axiom audit, mutants; on `main` through `scripts/release claims`, which records the result), before it is wired into a verb; a spec for such work lists its theorems first. Existing kernels that are only tested are backfilled with proofs. The laws those decisions obey live in `proofs/Calculus` (plain Lean, a doc comment on each) and are listed in the generated [`docs/writfold/laws.md`](docs/writfold/laws.md): new or changed decision logic states its law there, links its kernel in `proofs/laws.toml` (or declares it out with a reason), and regenerates the page with `python3 proofs/laws_page.py --write` in the same commit; both gates refuse a translated function that is neither linked nor declared out (the backlog closed in v0.6.0-dev.29, #213), and the quality gate refuses a stale page or assurance table. A new kernel names the core operation it implements and is linked to it before it is wired; a kernel with no law above it is declared out with a one-line reason. Parsers, file and Git IO, rendering and numeric plumbing stay tested-only, and each spec says which parts those are. One TLC model per real protocol with crash points. Prefer property tests, kill/fault-injection tests and the "removing this check fails a test" discipline.
- Apply the size budgets in `crates/writfold-xtask` (writfold-app modules ≤250 lines, functions ≤80, tests included); no `unwrap`/`expect`.
- **tauten (a quality-gate step).** Each crate declares a tauten tier; [`AGENTS.tauten.md`](AGENTS.tauten.md) is the strictness profile (cargo-tauten 0.2.0, the version pinned in `toolchains.lock.json`) and [`docs/writfold/tauten-adoption.md`](docs/writfold/tauten-adoption.md) the current state and history. The quality gate's `tauten-check` step runs `cargo tauten check`: findings in `tauten-baseline.json` are accepted, new error-level ones fail, and so does a `proofs/claims.json` recorded before the last change under `crates/writfold-core/` or `proofs/`. `scripts/tauten-check` runs the same check locally. Do not grow the baseline (`--allow-increase`) to make a task pass. For a kernel or proofs change, `scripts/release claims` is the proofs gate that lands it on `main`: it runs the drift check, `lake build`, the axiom audit and the mutants, and records `proofs/claims.json`; commit the record before the quality gate (the compose proofs run and `cargo tauten proofs try` are the developer loop and record nothing). Kernel arithmetic and indexing inside functions with a proved total theorem are subsumed through that record. Where the profile and this file disagree, this file wins: kernel arithmetic and indexing in extracted code are left to the proofs, frozen components are not rewritten for it, and an exception is `#[expect(lint, reason = "...")]` (shared test helpers keep a reasoned `#![allow(dead_code)]`).
- Before pushing main, run `scripts/gate quality` and `scripts/gate unit` from main (never from agent worktrees; run `git ls-files -z | xargs -0 touch` first). Record the receipt paths in the commit message; do not add receipt-index commits. Running them as `writfold kb gate run quality|unit` (definitions in `.writfold/gates/`) records KB receipts, and `writfold kb gate lines` prints the commit-message lines.
- Build locally through Compose/BuildKit. Reuse the operator's storage binding and admission floors; never relocate storage, prune unrelated resources or install publishing secrets on build workers.
- **Issues, milestones and RFCs (owner, 20 November 2026).** All remaining and future work is a GitHub issue in a milestone; a commit that does it names the issue (`Refs #N`, `Closes #N` on the last). Designs that are costly to reverse, and any new or changed decision logic, are RFCs in `docs/rfcs/` ([process](docs/rfcs/README.md)) with their proof obligations first. Since 21 November 2026 the owner accepts RFCs by default: an agent marks one `accepted` with a decision-log line, implements it, and the owner reviews and amends afterwards; do not stall work waiting for acceptance. Planning that used to go into `docs/writfold/*-spec.md` now goes into an RFC. Close an issue only when the work is on `main` and gated; never close one to make a count.
- Update current documentation alongside implemented changes. Public website copy may describe only exercised capabilities; anything else is labelled planned.
