# RFC: `find`: what to build next (measured)

> **Status:** research, 17 November 2026, against `main` at `33b5032`. Nothing here is built. Every number comes from a scratch prototype (environment switches patched into a copy of the tree, deleted afterwards) or from SQLite driven directly. Semantic embeddings are out of scope: they were measured and deferred in [semantic-search-spike.md](2026-11-16-semantic-search-spike.md) and [mission.md](../writfold/mission.md).

## The question

`find` runs at session start, before the first prompt, so a lookup has to hit on the first try and be cheap. Which lexical, structural and ergonomic changes raise hit@1 and hit@5, at what cost in latency, index size and dependencies, and which are not worth building?

## Summary

1. **Stemming is the largest single gain and costs nothing at query time.** Changing the word table's tokenizer to `porter unicode61 remove_diacritics 2` took hit@1 from 44 to 55 of 84 on the constructed set, with no measurable latency or size change. No new crate.
2. **Three small tiers add 14 more hit@1 on top of stemming**: acronyms derived from names (+6), `<name> <kind word>` answered through the graph (+4), a one-typo correction of body words against the index vocabulary (+4). Aliases on every record add 4 more, for 73 of 84.
3. **Context must only reorder inside the name tiers.** Putting the current project first inside every tier fixed 3 of 3 ambiguous lookups but cost 3 to 4 hit@1 elsewhere; restricted to the name tiers it fixed the same 3 and cost nothing.
4. **Latency is dominated by work that scales with the KB, not by SQLite.** On 3,000 records an exact ID lookup takes about 37 ms, of which 15 ms is fixed (process, Git, opening the index) and about 20 ms is scanning every section name and every title for tiers that cannot outrank the exact hit. Stopping after an exact ID hit gives 12 ms; a derived names table removes most of the rest.
5. **Nothing lexical fixes paraphrase.** Meaning-only queries stayed at 0 of 12 and 1 of 4 hit@1 under every variant. That residue is the case for the deferred semantic tier, and it is small next to the gains above.
6. **No crate earns an exception.** `fst`, `strsim`, `nucleo-matcher` and `tantivy` each solve a problem this index does not have at its size.

## Method

**Binary.** Host release build (glibc) of `33b5032` plus the prototype patch. The published budget in [validation](../guide/validation.md) is for the musl binary, whose allocator costs about 1.5 to 1.8 times more, so compare the deltas here, not the absolute values.

**Timing.** Process start included, `--json`, 25 calls per case with all variants interleaved in one loop. The host was shared and heavily loaded (load average 30 to 50), so medians moved by 2 times between runs. The tables give the **minimum** of the 25 calls, which was stable to about 2 ms between runs. p95 on this host was 1.5 to 4 times the median and says nothing about the code.

### Notes on individual results

**Stemming.** One stemmed table, same `text` tier. FTS5's `porter` is English only. One TYPB phrase lost rank 1 (it stayed in the first five); the cause was not traced. With one table an exact word no longer outranks its stem inside BM25. Keeping both an unstemmed and a stemmed table would preserve that order at +7.8 MB (+34%) on the bench; nothing measured here justifies it. Stemming breaks today's `match:` line: the line is found by plain containment of the query's words, and `migrating` is not contained in "migrations". In the prototype those rows fell back to a bare tier label. The fix is FTS5's `highlight()` on the body column, taking the line of the first marker: +1.5 ms for 50 hits (5.9 ms against 4.4 ms in SQLite alone).

**Acronyms.** A query token is the initials of consecutive name tokens (ID, ID after its prefix, last segment, title, alias), with and without stop words, in order with the existing prefix rule for the other tokens: `PITR`, `SLOs`, `BG deploys`, `SSO lantern`. A single-token query needs three letters; in a longer query two. Over the 112 phrases of both sets the tier produced 11 rows on 7 phrases, and on all 7 an expected record was among them: no spurious row. On the bench (random five-word titles) `wal`, `api`, `log` and `cpu spike` produced none.

**Kind words.** `quay-worker tickets`, `signatures for quay-worker`, `HBR-110 investigation`: when the first or last word names a kind and the rest resolves exactly or by `normalized`, the neighbours of that record of that kind are listed, each with its edge (`linked concerns quay-worker`). This is query understanding plus one edge lookup, not a ranking model.

**Body typos.** For each query word absent from the index vocabulary, the nearest indexed terms within the existing tolerance (one edit, two above eight characters; at most three terms, by distance, then document count) replace it, and the every-word query runs again as its own tier before `text-any`. Multi-word phrases with one misspelled word already hit through `text-any` (6 of 6 at baseline), so the gain is on single words and on ranking. Reading the vocabulary through `fts5vocab` is too slow: 21.6 ms per unknown word on 22,426 terms, against 2.6 ms from a plain two-column table of the same terms. A trigram table with `detail=full`, the other way to do this, is 19.2 MB against 7.8 MB.

**Aliases.** One front-matter key on Markdown records, read into the existing alias table, so `exact`, `normalized`, `prefix` and the acronym tier see it. Front matter is already part of the indexed body, so an alias's words also reach `text` and `text-any` without further work; a separate weighted column added one phrase. Two measured cautions:

- An alias answers its own wording and close variants, not the concept: `canary flag rollout` stayed at rank 2 to 5 behind a runbook with "canary" in its name.
- An alias attracts other phrases that share its words. On the independent set `zero downtime signing key rollover` fell from rank 1 to the first five once another record carried the alias `zero downtime deploys`.

Scored on the phrases they were copied from, aliases gave 10 of 10 (from 3 of 10).

**Context.** The prototype put hits belonging to a given project first inside a tier (the record's project, its path, or one edge away from a record of the project). Inside BM25 tiers that overrides relevance and loses 3 to 4 hit@1 on unrelated phrases. Inside the name tiers only (`exact` with several candidates, `normalized`, `prefix`, `acronym`, `heading`) it fixes all three ambiguous lookups and changes nothing else under either project. A tie-break alone would not have fixed `flush stalls`: the out-of-project title had fewer leftover words.

## Results: latency

3,000-record bench, minimum of 25 interleaved calls, ms, glibc.

| Variant | `SYN-1234` | `ledger flush` | five-word free text | three-word miss |
|---|---:|---:|---:|---:|
| baseline | 39.1 | 32.0 | 43.6 | 51.0 |
| stemming | 37.1 | 29.5 | 41.7 | 48.6 |
| stemming + acronym + kind word + body typo + prefix words + stop words | 38.9 | 35.4 | 54.7 | 59.2 |
| the same with a `prefix='2 3'` index | 39.5 | 35.7 | 56.0 | 60.1 |
| acronym tier alone | +1 | +1 | +1 | 0 |
| body typo alone (60-word vocabulary) | 0 | 0 | +12 | +7 |
| body typo alone (22,426 terms, through `fts5vocab`) | 0 | 0 | +40 | +31 |
| context, name tiers | 0 | 0 | 0 | 0 |
| row limit 5 | 32.2 | 17.3 | 39.9 | 49.1 |
| stop after an exact ID hit | **12.2** | 29.7 | 41.7 | 49.3 |

Where an exact lookup spends its time (one instrumented call, ms): load name forms 2.5, `normalized` 0.6, `prefix` 1.8, **`heading` 7.5**, `text` 0.4, `substring` 0.3, **`typo` + `text-any` + building rows 12.8**. The fixed part, measured as `kb index status`, is 14.9 ms; `--version` is 2.0 ms.

Two scans account for most of it, measured in SQLite alone:

| Scan | Today | Alternative |
|---|---:|---:|
| every section with its record (9,000 rows, a correlated subquery each) | 9.5 ms | 0.3 ms for the distinct names (3 on the bench, 137 of 257 on the constructed KB), then only the matching sections |
| `id, title, path` of every file from the trigram table, whose rows carry the body | 4.7 ms | 1.5 ms from `records` |

**One process for several lookups.** `find --eval` is the only way to run several today: 1, 8 and 32 queries took 36, 178 and 699 ms, so about 21 ms per query after 15 ms of start-up. Eight lookups in one process cost 178 ms against 8 × 37 = 296 ms in eight. With the row limit and the exact stop the same eight took 75 ms. On the 93-record KB one `find` is 12 ms and 84 lookups in one process are 143 ms (1.6 ms each).

**Cold cache.** With the index, the binary and the KB's files evicted from the page cache (`posix_fadvise`, seven tries): 3,000 records 173 to 239 ms cold against 37 to 50 warm; 93 records 47 to 59 ms cold against 12 to 17 warm. The first lookup after a reboot costs about four times a warm one. Only the index pages matter at that size, so a smaller index is the lever.

## Results: crates

Not built; these are properties of the crates, set against what was measured above.

| Crate | Buys | Against SQLite at this size | Cost |
|---|---|---|---|
| `strsim` | edit distances | `diag::distance` already exists in `writfold-core` | already in `Cargo.lock` transitively; a second, unproved distance |
| `fst` (with Levenshtein automata) | fuzzy lookup over a term set in microseconds | a 22,426-term table scans in 2.6 ms; worth it beyond roughly 200,000 distinct terms | 1 to 2 crates, pure Rust, musl-clean; a second derived file or a blob to keep equal to a rebuild |
| `nucleo-matcher` | subsequence matching (`hbapi` → `harbor-api`) | useful for interactive typing in `watch`, not for a hook | 2 to 3 crates |
| `rust-stemmers` | Snowball stemmers for non-English text | FTS5 Porter covers English; needs a custom FTS5 tokenizer through `rusqlite` | 2 to 3 crates; revisit for a non-English KB |
| `tantivy` | BM25F, fuzzy terms, stemmers, fast phrases | none of these is the bottleneck: SQL is under 7 ms of a 40 ms lookup | on the order of 100 crates and several MB; its own multi-file index, which breaks "one derived SQLite file" and `index verify`'s table equality |

Recommendation: no exception.

## Recommendation, in order

1. **Hook path: `--limit N`, stop after an exact ID, and a batch form.** Rows are a prefix of today's answer, so no ranking changes. ID lookups drop from 37 to 12 ms; eight lookups in one process from 178 to 75 ms.
2. **Porter stemming, with `highlight()`-based match lines.** +11 hit@1, no latency, no size. Schema and extractor versions bump; every golden with a `text` row is re-blessed.
3. **Aliases on every record** (already first on the roadmap), then **alias proposals from misses**. Add a lint warning when an alias shares all its words with another record's name or alias, since that is the measured way an alias steals a phrase. Mine two cheap proposal sources as well: "Full Phrase (ABC)" patterns in bodies, which is the only route to `OIDC`, and the words on the line of a mention next to the record's ID.
4. **Acronym tier**, after `prefix`.
5. **Kind-word tier**, after `exact`.
6. **A derived `names` table and a vocabulary table.** Normalized name forms with their record, rank and tokens; distinct section names; indexed terms with document counts. This turns `normalized`, `prefix`, `acronym`, `heading`, `typo` and the suggestions into index reads, and is what makes item 7 affordable. Fold in the shared external-content table (−27% index, which is also the cold-cache lever).
7. **Body typo tier** over the vocabulary table, compared against unstemmed terms.
8. **Context order in the name tiers**, fed by the session-start hook (project from `cwd`, the current run's project), with a `because` key beside `matched_on`.
9. **Session-start lookups from what is already known**: ticket-shaped tokens in the branch name and the run's task, the repository name against asset locators; `exact` tier only; each hit shown with its bounded, labelled neighbours.

**Drop:** the `prefix=` index; prefix words in the word table; the stop-word and phrase tiers (0 alone, −2 hit@1 on top of the other tiers); BM25 retuning (±1, within noise of a small set); `detail=column` or `none` on the word table; a `detail=full` trigram table; context ordering inside text tiers; every crate above.

**Keep deferred:** the semantic tier. After items 1 to 8 the constructed set's remaining first-five misses are 4 of 84, three of them paraphrase or body-only acronyms; the independent set's 11 misses are all meaning-only. Revisit with a query file grown from real misses.

## Explaining a row

`matched_on` names the tier. Three additions keep every new behaviour deterministic and legible:

- **`because`**, an array of short fixed strings beside `matched_on`, for anything that moved or added a row without matching text: `project:lantern` (context order), `linked:concerns:quay-worker` (kind word), `corrected:nulable→nullable` (body typo), `initials:P-I-T-R` (acronym). Absent when empty, so existing consumers see no change.
- **Context is an input, not ambient state.** The hook passes `--context project=<name>`; the trailer's `q=` digest covers it. The same command line gives the same rows.
- **Neighbours are lines, not rows.** A strong hit (`exact`, or the only `normalized` hit) may carry up to five `linked:` lines (decision → tickets, investigation → signature), in edge-key order, with `+N more`. `shown`, the ranks and `find --eval` are unaffected.

## Lean theorems each change needs

Tier order itself needs nothing new: every hit still passes `find::admit`, and `admit_iff`, `full_admits_nothing` and `not_full_admits` (`Walk.lean`) already say a record is shown once, under the first tier that found it, within the limit.

| Change | Kernel (`writfold-core::find`) | Theorems |
|---|---|---|
| `--limit N` | `full` (exists) | `limit_prefix`: the rows under limit `n ≤ m` are the first `n` rows under `m` |
| Stop after an exact ID | `exact_stops(id_shaped, exact_hits)` | `stops_only_on_one_exact`; `stop_is_prefix`: the answer is the first row of the full answer |
| Stemming | none (tokenizer and match line are text plumbing, tested) | none; a test that every `text` row carries a cited line |
| Aliases on records | none (existing `normalized` and `prefix` kernels) | none new |
| Alias proposal from a miss | `propose(answer_rows, cited, resolves_exactly)` | `proposal_only_after_miss` (the cited record was not in the first five rows); `no_proposal_when_phrase_names_another`; a proposal is never a write (by type, as for other proposals) |
| Acronym tier | `initials(query, name, single_min, multi_min)` over code points, beside `prefixed` | `initials_spec` (a match is an in-order embedding where each query token begins one name token or is the initials of consecutive ones); `initials_uses_initials` (never a pure prefix match, so the tier is disjoint from `prefix`); `short_never_matches`; `leftover_le_name` |
| Kind-word tier | `kind_word(tokens)`; `linked_ok(anchor_tier, neighbour_kind, named_kind)` | `kind_word_first_or_last`; `rest_nonempty`; `linked_needs_anchor` (only `exact` or `normalized` anchors); `linked_kind_equal`; `anchors_le_three` |
| Body typo tier | `correct(known, candidates, tolerance)` | `known_word_kept`; `replacement_within_tolerance`; `at_most_three`; `unchanged_query_no_tier`; order is total (distance, then count, then term) |
| Context order | `context_order(tier_is_name, in_context[])` → a permutation | `context_same_tier` (output is a permutation of the tier's hits); `context_stable` (order kept on each side); `context_none_identity`; `text_tiers_untouched` |
| Neighbour lines | `neighbours(strong, edges, k)` | `neighbours_bounded`; `never_rows` (`shown` unchanged); with the existing rule that a pointer is not evidence |
| `names` and vocabulary tables | none (derivation) | none; `index verify` gains the tables; a property test that each tier answers as the scan did |

Each kernel is written and proved before it is wired in, with one mutant per check, as for `admit` and `prefixed`.

## Build plan (outline)

1. *(Note, 20 November 2026: built in v0.6.0-dev.11 as [#19](https://github.com/writfold-dev/writfold/issues/19) with the independent set, since the constructed phrases were not kept; see [validation](../guide/validation.md#lookups-find---eval).)* **Query file first.** Commit the constructed phrases as a fixture overlay (not in `fixtures/kb/basic`, which would move every golden's `kb=`), with the class in `note`, and print hit@1 and hit@5 per class from `find --eval`. Every later step states its delta on it and on the fixture set.
2. **Hook path.** `--limit`, the exact stop and `find --batch FILE|-` (one answer per phrase, one trailer each). Proofs: `limit_prefix`, `stop_is_prefix`. Budget test: count work, not time. The host measured here swings 2 to 4 times, so an absolute timing test would flake; assert through SQLite's statement counters that an exact ID lookup performs no full-table scan step, and keep one generous wall-clock ceiling.
3. **Stemming.** Tokenizer, `highlight()` match line, schema and extractor bump, goldens re-blessed, `validation.md` and `kb-layout.md` tier table updated.
4. **Aliases everywhere, then proposals.** Front-matter key, the alias-collision lint, the proposal kernel and its two extra sources.
5. **`names`, section-name and vocabulary tables; shared content table.** Property tests against the scans; `index verify` extended; re-measure the bench and restate the budget.
6. **Acronym, kind-word and body-typo tiers**, each as kernel, proof, mutants, wiring, golden, guide row, eval delta.
7. **Context and `because`.** `--context`, the stable partition in name tiers, JSON key, hook passing the project.
8. **Session-start lookups.** Names from branch, run task and repository; `exact` only; neighbour lines; inside the existing 9,000-character cut, dropped before the brief.

## Other findings

- **Outside Git every read rebuilds the index**: `index=rebuilt` on each call, about 200 ms on 3,000 records, against 37 ms inside Git.
- **A copied KB is slower until Git refreshes its index.** After `cp -r`, each call paid about 15 ms more because the copied Git index's stat data no longer matched the files; one `git status` removed it. A KB copied into a container or CI job will see this.
- **`fts5vocab` is not a cheap table**: an equality probe is 0.01 ms, a filtered scan of 22,426 terms 21.6 ms.
- **Section names repeat heavily** (3 distinct of 9,000 on the bench, 137 of 257 on the constructed KB), which is why matching distinct names first pays.
