# RFC: Loops: a plan step that repeats a template until its gates are met

## Summary

A plan step may be a **loop**: `loop=<template>` with a required `max=N` and
an optional `min=N`. The template is the loop's body. One copy of it is
spliced under the step when the plan is spliced (as `use=` does today), and
each further copy, a **round**, is spliced by a new verb, `writfold kb plan
again`. The step's own gates are the exit: the step is advanced, as any
step is, when every one of them is met and at least `min` rounds were made.
`plan again` is refused once `max` rounds exist. A loop that used every
round without meeting its gates is **spent**: it stays open and owing, and
the only ways to close it are the ones that exist already and are never
shown as done (`plan skip`, a waiver the gate's `accept` takes).

Nothing else is new. There is no loop file, no loop state, no scheduler and
no clock. A round is an ordinary splice event; how many rounds were made is
the number of such files; "may the agent leave the loop" is `plan advance`.
Writfold still only records: it never runs a body and never starts a round.

What does not change: a template without `loop=` reads, splices and folds
exactly as before; `plan use --again` keeps its meaning; `handoff check`
takes no plan input and so cannot be weakened by a loop.

The criticism section argues that a first-class loop concept is not
suitable for Writfold, and that this smaller extension is. It also says
where even this may be more than the owner needs.

## Proof obligations

- **Kernel:** new module `writfold_core::plan::round`
  (`crates/writfold-core/src/plan/round.rs`, in the Charon `start_from`
  list; `loop` is a Rust keyword, and "round" is the word shown to users).
  Nothing in it reads a file or a clock.

  ```rust
  pub const MAX_ROUNDS: usize = 32;
  pub struct Bounds { pub min: usize, pub max: usize }
  /// 1 <= min <= max <= MAX_ROUNDS.
  pub fn bounds_ok(b: &Bounds) -> bool;
  /// A loop can end on something: a gate on the step, or min above 1.
  pub fn has_exit(b: &Bounds, gates: usize) -> bool;

  pub enum Exit { Met, Again, Spent }
  /// Met: rounds >= min and every gate met. Else Again while rounds < max.
  /// Else Spent.
  pub fn exit(b: &Bounds, rounds: usize, met: &[bool]) -> Exit;

  pub enum AgainRefusal { Complete, NotCurrent(usize), NotLoop, Met, Spent }
  /// Whether the next round may be spliced under step `at`; Ok carries
  /// its number, rounds + 1.
  pub fn again_check(nodes: &[Node], at: usize, looped: bool, b: &Bounds,
                     rounds: usize, met: &[bool]) -> Result<usize, AgainRefusal>;

  pub enum Refusal { Plan(super::Refusal), Rounds(usize) }
  /// `plan advance` on a loop step: the plan kernel's refusals first
  /// (complete, not current, a gate owed), then the rounds still owed
  /// (min - rounds).
  pub fn advance_check(nodes: &[Node], at: usize, b: &Bounds, rounds: usize,
                       met: &[bool]) -> Result<(), Refusal>;

  pub struct Place { pub round: usize, pub rounds: usize }
  /// A step of a round that is not the newest round of its loop.
  pub fn superseded(place: &Place) -> bool;
  /// Some enclosing round on the step's path is superseded.
  pub fn superseded_any(path: &[Place]) -> bool;
  /// `plan::stale`, except that a superseded step is never stale.
  pub fn stale(node: &Node, met: &[bool], superseded: bool) -> bool;
  /// More rounds exist than max allows (a merge of two clones).
  pub fn over(b: &Bounds, rounds: usize) -> bool;

  pub enum Next { Advance, Judge(usize), Again, Report }
  /// What a loop step's `next:` line names. `judged[i]`: gate i has a
  /// verdict about the present bytes (failed, unknown, an unsupported
  /// checklist item), as opposed to open or stale.
  pub fn next(b: &Bounds, rounds: usize, met: &[bool], judged: &[bool]) -> Next;
  ```

- **Theorems** (`proofs/Writfold/Round.lean`), each for every input:
  - `exit_met_iff`: `exit b r met = Met` iff `r ≥ b.min` and every `met[i]`.
  - `exit_again_below_max`: `exit b r met = Again` implies `r < b.max`.
  - `exit_spent_iff`: under `bounds_ok b`, `Spent` iff `r ≥ b.max` and some
    gate is not met.
  - `again_admitted_iff`: `again_check … = Ok n` iff `plan::current nodes =
    some at`, `looped`, and `exit b r met = Again`; then `n = r + 1`.
  - `again_bounded`: `Ok n` implies `n ≤ b.max`. No sequence of admitted
    rounds exceeds `max`.
  - `again_refusal_order`: the refusal is the first that applies of
    `Complete`, `NotCurrent`, `NotLoop`, `Met`, `Spent`.
  - `advance_iff`: `advance_check … = Ok` iff `plan::current nodes = some
    at` and `exit b r met = Met`.
  - `advance_implies_plan_advance`: `Ok` implies `plan::advance_check nodes
    at met = Ok`. A loop never advances a step the plan kernel would refuse:
    declaring a loop cannot weaken a step's gates.
  - `spent_never_advances`, `spent_never_again`: with `exit = Spent`, both
    checks refuse. Running out of rounds is never a way through.
  - `again_advance_exclusive`: on the same inputs the two checks are never
    both `Ok`.
  - `loop_step_progress`: when `at` is the current step and `looped`,
    exactly one holds: `advance_check = Ok`, `again_check = Ok`, or
    `exit = Spent`.
  - `one_round_is_plain`: with `b = {min: 1, max: 1}`, `advance_check`
    agrees with `plan::advance_check` and `again_check` is never `Ok`.
  - `superseded_iff`: `superseded p` iff `p.round < p.rounds`;
    `superseded_any_iff`: some element is superseded.
  - `superseded_never_stale`: `stale n met true = false`;
    `newest_round_unchanged`: `stale n met false = plan::stale n met`.
  - `over_iff`: `over b r` iff `r > b.max`.
  - `next_advance_iff`: `Advance` iff `exit = Met`.
  - `next_judge_first`: `Judge i` implies `i` is the first unmet gate and
    `judged[i] = false`; an unjudged first owed gate is always named before
    `Again` or `Report`.
  - `next_again_implies_admissible`: `Again` implies `exit = Again`.
  - `next_report_implies_spent`: `Report` implies `exit = Spent`.
  - Totality of every function (`proofs/Total.lean`).
- **Mutants** (`proofs/mutants.py`):
  - `round-exit-ignores-min` (drop `r ≥ min`): breaks `exit_met_iff`,
    `advance_iff`.
  - `round-again-ignores-max` (drop `r < max`): breaks
    `exit_again_below_max`, `again_bounded`.
  - `round-again-at-max` (`r <= max`): breaks `again_bounded`.
  - `round-again-when-met` (drop the `Met` refusal): breaks
    `again_admitted_iff`, `again_advance_exclusive`.
  - `round-again-any-step` (ignore `looped`): breaks `again_admitted_iff`.
  - `round-advance-when-spent` (treat `Spent` as `Met`): breaks
    `spent_never_advances`, `advance_implies_plan_advance`.
  - `round-advance-skips-gates` (rounds only): breaks
    `advance_implies_plan_advance`.
  - `round-superseded-newest` (`<=`): breaks `superseded_iff`,
    `newest_round_unchanged`.
  - `round-stale-ignores-superseded`: breaks `superseded_never_stale`.
  - `round-next-again-before-judge`: breaks `next_judge_first`.
- **Unchanged and already proved:** `plan::current`, `plan::skip_check`,
  `plan::splice`, `plan::splice_check` (the depth bound),
  `policy::close`, `policy::summary`, `policy::met`, `handoff::strict`. A
  loop step is closed by the same two records as any step, so how it
  closed and the plan's summary word need no new case.
- **Tested and unproved:** reading `loop=`, `max=` and `min=` from a step
  string and the diagnostics; the closure and the snapshot; counting rounds
  (valid splices of the loop's template under the loop's node) and each
  step's `Place` in the fold; reading the body from the run's snapshot;
  the write (the existing splice write plan); rendering, JSON and lint.
  Each is covered by an integration test where removing the check fails it
  (`crates/writfold-kb/tests/plan_loop.rs`, `plan_loop_recheck.rs`).
- **Model:** a round is written by the protocol `spec/RunGraph.tla` already
  models (one create-new splice at the next ordinal under a parent, decided
  outside the lock and re-checked under it). No new protocol and no new
  crash point. The bound is a new property across sessions, so the model
  gains it: a `PlanAgain` action, the invariants `RoundsWithinMaxLocal`
  (rounds written in one clone never exceed `max`) and
  `RoundOnlyAtLoopStep`, the probe `RoundsWithinMax` (which a merge of two
  clones breaks, as `SpliceIdempotent` does today), and the mutant
  `AgainIgnoresMax`.

## Motivation

The owner asked for a way to say, as part of the execution graph, "repeat
this until X", with X configurable: a count, a script, a quality bar.

Three things in today's run graph show the gap; each can be reproduced with
the existing fixtures.

1. **Nothing bounds or declares repetition.** `plan use review --again`
   splices another copy for as long as it is asked. The template cannot say
   "at most five". The repetition lives in a skill's prose, which Writfold
   does not read.
2. **A cold session is not told to go around.** A step owing `unit
   [failed]` prints `next: writfold kb gate run unit`. Running the check
   again cannot change the answer; the agent has to know, from somewhere
   else, that the fix-and-review sub-steps should be done again.
3. **Repeating makes the plan read stale.** After `review#1` is done and
   the code is fixed, `review#1`'s gates no longer hold for the present
   bytes, so the plan can end only as `complete-stale` (exit 2), although
   `review#2` is the review that counts
   (`crates/writfold-kb/src/plan/summary.rs`: any done step with an unmet
   gate).

Prior art (public documentation, found by web search on 21 November 2026;
the primary documents were not re-read in full) agrees on the
shape and on the failure to avoid:

- Ansible's `until` / `retries` on a task is the closest: a condition, and
  a required finite cap; a task that runs out of retries **fails**, it does
  not pass.
- LangGraph cycles end on a stop condition or raise `GraphRecursionError`
  at `recursion_limit` (default 25): running out is an error, never a
  normal end.
- AutoGen combines termination conditions (`MaxMessageTermination |
  TextMentionTermination`): a count beside a content condition, whichever
  fires first; the result does not always say which one ended the run.
- Claude Code's Ralph loop plugin re-feeds a prompt from a Stop hook until
  the model prints a "completion promise" or `--max-iterations` is reached.
  The promise is text the looping agent writes itself, and the iteration
  cap is optional. Both are what Writfold must not copy: an exit the agent
  can state without evidence, and a loop with no bound.
- CI systems (GitHub Actions, Argo `retryStrategy`, Temporal retry
  policies) retry a failed step up to a limit and report the final attempt;
  attempts are records, not graph nodes with their own obligations.

The lessons taken: the cap is required; the exit is evidence, not the
agent's word; and exhausting the cap is a distinct, non-passing outcome.

## Behaviour

Output below is the design. No binary has produced it yet.

### Declaring a loop

```toml
# .writfold/plans/fix.toml
schema = "writfold-plan/1"
name = "fix"
steps = [
  "reproduce: repro",
  "converge: unit review loop=attempt max=5",
  "deliver: deliver:pr-comment",
]
```

```toml
# .writfold/plans/attempt.toml: one round
schema = "writfold-plan/1"
name = "attempt"
steps = [
  "change:",
  "read-diff: diff-read",
]
```

- `loop=<template>` names the body. `max=N` is required, 1 to 32. `min=N`
  is optional, 1 to `max`, default 1.
- The step's gates are the exit. Any class works, which gives every exit
  the owner listed without a new mechanism:

  | Exit wanted | Written as |
  |---|---|
  | a script's exit code | a `mechanical` gate on the step (`argv`, or a script shipped with `{gate}`) |
  | something in the world (CI green) | an `observed` gate, with `ages_as` if it should lapse |
  | a quality bar | a `checklist` gate: every required item covered `supported` with grounded evidence; `accept = ["attested"]` to refuse a waiver |
  | someone says so | an `attested` gate with `instructions` |
  | the run's records show it | a `run-record` gate |
  | a count | no gate: `loop=attempt min=3 max=3` is exactly three rounds |
  | several at once | several gates on the step: all must be met |
  | give up after N | `max=N` (always present) |

- Refused when the template is read (`plan set`, `plan use`, `kb lint`),
  each at the word:

  | Code | When |
  |---|---|
  | `key.missing` | `loop=` without `max=` |
  | `key.not-here` | `max=` or `min=` without `loop=` |
  | `key.range` | `max` outside 1..32, or `min` outside 1..`max` |
  | `value.twice` | a second `loop=`, `max=` or `min=` |
  | `value.conflict` | `loop=` beside `use=`, `deliver:<mode>` or `posted:<mode>` on one step |
  | `value.no-exit` (new) | a loop with no gate and `min` of 1: it has no exit of its own; write `use=` |
  | `ref.undefined`, `ref.cycle` | as for `use=`: the body must exist, and a loop inside its own body or a nesting past four levels is refused |

- A warning (`kb lint`; exit unchanged without `--deny-warnings`):
  `policy.self-exit`, when every gate of a loop step is `attested` or
  `checklist` class, or accepts a waiver: whoever walks the loop can then
  also end it with a statement.

### Walking it

`plan set fix` splices `attempt#1` under `converge`, as `use=attempt`
would. After the first round, with `unit` failing:

```text
$ writfold kb plan status
step fix#1/reproduce [done] repro [satisfied] @runs/run-…/plan/done-fix.1~reproduce.json:1
step fix#1/converge/attempt#1/change [done] no gates @runs/run-…/plan/done-fix.1~converge~attempt.1~change.json:1
step fix#1/converge/attempt#1/read-diff [done] diff-read [attested] @runs/run-…/plan/done-fix.1~converge~attempt.1~read-diff.json:1
step fix#1/converge [current] owes: unit [failed], review [open] @runs/run-…/plan/splice-fix.1.json:1
  loop: attempt, round 1 of at most 5
  next: writfold kb plan again
step fix#1/deliver [later] gates: deliver:pr-comment @runs/run-…/plan/splice-fix.1.json:1
```

The `next:` line is `round::next`: while the first owed gate has no verdict
about the present bytes (`open`, `stale`), it names that gate's own command
(`writfold kb gate run unit`); once it has one and is not met, it names
`plan again`; when the exit holds, `plan advance`.

```text
$ writfold kb plan again
step fix#1/converge/attempt#2/change [current] no gates @runs/run-…/plan/splice-fix.1~converge~attempt.2.json:1
  next: writfold kb plan advance
step fix#1/converge/attempt#2/read-diff [later] gates: diff-read @runs/run-…/plan/splice-fix.1~converge~attempt.2.json:1
step fix#1/converge [later] gates: unit, review; loop: attempt, round 2 of at most 5 @runs/run-…/plan/splice-fix.1.json:1
# note: round 2 of at most 5 under fix#1/converge, because unit [failed] @runs/run-…/gates/unit-….json:1; recorded runs/run-…/plan/splice-fix.1~converge~attempt.2.json
```

`plan again [--run ID] [--repo DIR]` takes no template: the loop names it.
It exits 0 when it wrote the round and 3, writing nothing, when refused:

| When | The refusal says |
|---|---|
| the plan is complete | `not repeated: every step is closed` |
| the current step is not a loop | `not repeated: <step> is the current step and is not a loop` (inside a round: `…; round 2 of fix#1/converge is under way`) |
| the exit holds | `not repeated: fix#1/converge owes nothing more (round 2 of at most 5): writfold kb plan advance` |
| the loop is spent | `not repeated: fix#1/converge has used its 5 rounds` |
| another session wrote first | the existing `the plan changed since this command read it (…); nothing written; rerun` |

`plan use attempt --again` at a loop step whose body is `attempt` is
refused and names `plan again`, so a round cannot be added around the
bound. Another template may still be spliced under a loop step with `plan
use`; it is not a round.

`plan advance` on a loop step refuses, as today, while a gate is owed. With
every gate met and fewer than `min` rounds it refuses with `not advanced:
fix#1/converge owes 2 more rounds (1 of at least 3)`.

### Leaving the loop

| How | Shown | Plan summary |
|---|---|---|
| the exit holds, `plan advance` | `[done]`, with the step's word `passed`, `attested` or `waived` from its done record, as for any step; the `loop:` line reads `attempt, 3 rounds of at most 5` | `complete` only if every gate passed a check |
| spent, then a gate is met without another round, `plan advance` | the same: met is met | the same |
| a gate is waived (where its `accept` takes a waiver), `plan advance` | `[done]`, word `waived` | `complete-with-exceptions` |
| `plan skip --reason TEXT --by WHO` | `[skipped]`, `loop: attempt, gave up after 5 of at most 5 rounds`, the reason and the name | `complete-with-exceptions` |
| nothing | `[current] … !spent` | `incomplete` |

A spent loop:

```text
step fix#1/converge [current] owes: unit [failed] @runs/run-…/plan/splice-fix.1.json:1 !spent
  loop: attempt, round 5 of at most 5; no round is left
  why: 5 rounds did not meet unit: stop and report; whoever owns the run decides how the step closes
```

There is no `next:` line on a spent loop whose owed gates are all judged.
As with a guard refusal, the agent is not told how to excuse itself; the
ways out are in the guide. A skipped or waived loop is never shown as
passed, by the existing rules (`policy::close`, proved). An `unskippable`
required template locks a loop step among its steps like any other.

### Earlier rounds are history

A step of a round that is not the newest round of its loop is
**superseded**. It keeps its `[done]` or `[skipped]`, shows `(round 1 of
3)`, and its gates are not judged again: it is never `!stale`, and it does
not make the plan `complete-stale`. The newest round's steps and the loop
step itself are judged as every step is. This applies only inside a
declared loop; an `--again` copy elsewhere is judged as before.

### In the other views

- `resume`'s plan line and the session-start plan position are cut from
  `plan status`, so they carry the `loop:` line: a cold session mid-loop
  reads the round it is in, the bound, what the exit owes and the next
  command, with no tool call. After a compaction the same lines are
  re-injected.
- A Stop rule on `step.met` (the existing nudge) already keeps a session in
  a loop: the step owes, and the nudge's text is the step's `next:`, now
  `plan again`. No hook change.
- `--json`: a loop step's row gains `"loop": {"template", "min", "max",
  "rounds", "exit": "met"|"again"|"spent"}`; a body step's row gains
  `"round"` and `"superseded"`. The trailer gains `loops=` and `spent=`.
- More rounds than `max` (two clones each added one, then merged) show
  `!over-max` on the loop step and `plan status` exits 2, like the other
  merge flags. Nothing is discarded; the loop is spent.
- `handoff check` is unchanged. It reads no plan, so a loop that gave up on
  `unit` is still refused by a receiver that requires `unit`.
- Later slices: `gate lines` and `runs --plan` counts, `watch`'s plan map,
  a guard requirement that lets a Stop rule go quiet on a spent loop.

### What an existing setup can notice

changes.md: new step words `loop=`, `max=`, `min=` and the verb `plan
again`; nothing changes for a template without them.

## Design

**Template.** `Step` gains `repeat: Option<Loop>` with the body's name and
its bounds (`crates/writfold-kb/src/plan/step_word.rs`). The schema stays
`writfold-plan/1`: none of the three words is a slug, so none could have
been read as a gate.

**Closure and round 1.** `loop=T` enters the closure exactly as `use=T`
does: `T` is resolved, cycle-checked, depth-checked, snapshotted and its
gates pinned when the template is spliced, and one copy is laid under the
step at ordinal 1. So a loop's first round costs nothing new, and a
`max=1` loop is `use=`.

**A round.** `plan again`, with the loop step current:

1. Fold the run; find the current step and its `Loop` from the run's
   snapshot (never the live template: the bounds and the body a run started
   with are the ones it keeps; `!template-moved` flags a later edit as it
   does today).
2. `rounds` = the valid splices of the body's template under the loop's
   node. Judge the step's gates as `plan advance` does.
3. `round::again_check`. Refused: exit 3.
4. Write one `splice-` event: parent the loop's node, the body at the
   snapshot's digest, the next ordinal, `"again": true`, and one new
   optional field, `"until"`: for each gate of the step, its standing and
   evidence path at this moment (why this round began). Read by older
   binaries as any splice; they ignore `until`.
5. Under the write lock, the existing re-check: the step is still current
   and nothing was spliced under it since. A lost race is the existing
   refusal.

No pin is needed beyond what the splice write plan already does: the
body's gates were pinned with round 1.

**Crash points.** The write is one create-new file (plus an already
present snapshot, skipped). Stopped before the publish: nothing happened;
run it again. Stopped after: the round exists, the current step is the
round's first step, and running `plan again` again is refused with "round
N is under way", writing nothing. A round is never written twice, because
the file is named by parent, template and ordinal.

**Fold.** Unchanged in order: a loop step's rounds are its children,
before it, in ordinal order. The fold adds each step's `Place` list (for
each loop on its path, which round it is in and how many there are). The
judge skips superseded steps, so the cost of a read grows with the newest
round, not with the number of rounds; the fold itself stays linear in the
files.

**Nesting.** A body may hold a loop. Each round is one splice level, and
the existing bound of four levels applies, so three loops can nest under a
root template. Steps are created only as rounds are made: at most `max`
times the body's steps per loop.

**Windows.** A step's run-record window still begins at the event that
began it. For a round's first step that is the round's splice; for the
loop step, the last event of the newest round.

**Out of scope, on purpose:**

- **Running anything.** Writfold does not execute the body, re-invoke the
  agent or wait.
- **A time or budget cap.** No standing in the plan kernel reads a clock,
  and one age rule for the places where a clock enters is open
  ([#45](https://github.com/writfold-dev/writfold/issues/45)). Writfold
  cannot see token spend at all. `max` is the cap.
- **Raising `max` mid-run.** The run keeps its snapshot. A recorded
  override is a follow-up needing an owner decision.
- **For-each** (one round per item of a list, CI's matrix). That is data
  driving the graph, not repetition until an exit.
- **A delivery as a loop's exit.** `deliver:<mode>` binds one candidate to
  one done step; a loop step refuses the word. A body step may owe one.
- **Backoff, delay, parallel rounds.**

## Battle criticism

Written to be argued with. Each point is a reason not to build this, and
what survives it.

**1. "This is already expressible."** Largely true. Today: a step
`converge: unit review use=attempt`, and a skill that says "if `unit`
fails, run `writfold kb plan use attempt --again`". The children come
first, the step's gates are judged after them, and `--again` adds a copy.
What that cannot do is exactly three things: bound the repetition, tell a
cold session to repeat (the `next:` line says to run the failing check
again), and end as anything but `complete-stale`. If the owner does not
hit those three in real use, this RFC is not needed. They are the whole
justification; nothing else here is new capability.

**2. "A loop concept beside gates, with its own files and verbs."** Not
suitable. A `.writfold/loops/<id>.toml` would need a body (a plan
template), an exit (gates), records per iteration (splices and receipts)
and a place in the graph (a step). Every part exists. A second
representation of the same facts is where two readers start to disagree,
which is the fault class #35 and #56 were about. Rejected.

**3. "Writfold records; the agent walks."** A loop construct in most
frameworks is a scheduler: it re-enters the body. If `plan again` ran
anything, or if a hook re-fed a prompt, this would break the boundary #57
restated. It does neither: it writes one file saying the agent chose to go
around, and refuses to write it past the bound. The risk is the name. A
reader who sees `loop=` may expect Writfold to drive it; the guide must
say in its first sentence that it does not.

**4. Infinite loops.** `max` is required and capped at 32; `again_bounded`
is proved; the two-session race is closed by the existing re-check and
create-new name. Two clones can each add the last round and merge to
`max + 1`: flagged `!over-max`, never hidden, and the loop is spent. What
is not bounded: an agent that never calls `plan again` and just keeps
editing and re-running the gate. That is not a Writfold loop, and nothing
in Writfold stops an agent from working. The bound limits what is
recorded as rounds, not effort.

**5. Agents gaming the exit.** The exit is the step's gates, so it is as
strong as those gates and no stronger. A loop on an `attested` gate ends
when the agent attests. A loop on a mechanical gate that accepts a waiver
ends when the agent waives. Both are shown for what they are (`attested`,
`waived`, `complete-with-exceptions`), `policy.self-exit` warns at lint
time, and `accept = ["satisfied"]` plus the Claude Code `ask` permission
on `gate attest` and `gate waive` close it for teams that want that. An
agent can also weaken the gate's script; Git shows the diff, the pin reads
`policy-moved`, and `handoff check` judges by the policy revision. No new
defence is added because no new attack is: the loop adds no way to be met
that a plain step lacks (`advance_implies_plan_advance`).

**6. Waivers and give-ups masquerading as success.** The opposite risk to
5: making "ran out of rounds" look like "done". `spent_never_advances` is
the proof; a spent loop closes only by `plan skip` (shown skipped) or by
its gates becoming met. There is deliberately no `on_exhausted =
"continue"` key. A team that wants "try five times, then carry on" writes
a skip, with a name and a reason, every time.

**7. Burning rounds.** An agent can call `plan again` before judging the
exit and waste a round. `next_judge_first` keeps the guidance honest, and
the `until` field records what each round began on, so a wasted round is
visible. It is not refused: for an attested exit there is no negative
verdict to wait for, and refusing would wedge those loops.

**8. State explosion.** 32 rounds of a 10-step body is 320 steps and
about 350 small files in one run. The fold is linear and superseded steps
are not judged, so `plan status`, `resume` and the session-start hook
(whose latency the owner feels on every session) pay for one round's
gates, as now. Nested loops multiply only as rounds are actually made.
`watch` must collapse superseded rounds or its plan map becomes noise;
that is a follow-up, and until it lands the map is long, not wrong.

**9. Supersession hides evidence.** A superseded round's failing gate is
no longer shown stale. That is the point, but it means a body step's gate
proves something only about the round it was done in. A check that must
hold at the end belongs on the loop step (the exit) or a later step. This
is the existing rule ("done is history; list the gate again on a later
step"), now load-bearing, and the guide must say so.

**10. Is "round" a third thing to learn?** Two words, one verb, one flag,
one `loop:` line, two new diagnostic codes. Against that: the template now says
what the skill prose used to, and a cold session reads it.

**Verdict.** A new first-class loop concept is not suitable for Writfold
and is rejected. The extension of the plan step is suitable, with one
honest caveat: it formalises a pattern that mostly works today, so its
value depends on the three gaps in point 1 being felt. Recommendation:
build the kernel and the first slice (declare, `plan again`, the status
line, supersession), use it for a week on real work, and only then build
the views and recipes. If the week shows the agent rarely loops under a
plan, stop there; the slice costs one kernel module and one verb to keep.

## Compatibility and reversibility

- A KB without `loop=` is unaffected: no file, digest or output changes.
- An older binary reading a template with `loop=` refuses it at that word
  (`value.form`: not a gate ID). A run whose snapshot holds one cannot be
  folded by an older binary: its plan reads invalid there. That is the
  cost of the feature for a mixed-version team, and the changes.md entry
  says it.
- A round's splice event is valid for an older binary (it ignores `until`),
  but that binary cannot read the snapshot it belongs to, per the above.
- Reverting: remove the words from templates. Runs that used them keep
  their records; the fold code would have to stay to read them.

## Alternatives

- **Do nothing; document the `use=` plus `--again` pattern.** Costs
  nothing and loses the bound, the `next:` line and a non-stale ending.
  The fallback if the first slice is not used.
- **A guard requirement only** (`rounds.left`), leaving plans alone. It
  could stop a session, but a guard is one harness's hook and fails open;
  the bound must be in the write path.
- **`plan advance` starts the next round by itself** when the exit is not
  met. One verb fewer, but then asking "may I leave?" writes to the plan,
  and a refused advance stops being a read. Rejected.
- **A loop file** (criticism 2). Rejected.
- **`until=` naming gates apart from the step's own.** Two lists of gates
  on one step with different meanings. The step's gates are already
  "judged after its children"; that is the exit.
- **An exhausted loop that auto-skips.** Rejected (criticism 6).
